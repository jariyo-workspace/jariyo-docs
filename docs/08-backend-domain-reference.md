# 자리요 백엔드 도메인 기준 문서

## 1. 문서 목적

본 문서는 자리요 백엔드 설계와 구현에서 가장 먼저 참조해야 하는 도메인 기준 문서다.

이 문서는 다음을 고정한다.

* 어떤 도메인이 존재하는가
* 어떤 상태와 권한 규칙을 보존해야 하는가
* 무엇이 바뀌면 안 되는가
* 다른 문서가 어디까지 이 문서를 따라야 하는가

세부 필드 카탈로그는 `02-data-model.md`, HTTP 계약은 `04-api-spec.md`를 참조한다. 다만 백엔드 설계 판단에서 도메인 경계와 상태 규칙이 충돌하면 본 문서를 우선한다.

## 2. 불변 조건

다음 항목은 현재 구현된 MVP 기준에서 변경하지 않는다.

* 공개 API의 요청과 응답 계약
* 예약, 대기, 현장 대기, 서비스 처리의 핵심 상태 전이
* 고객과 운영자의 권한 경계
* 멱등성 적용 대상과 재사용 검증 원칙
* 동시성 충돌을 치명적 데이터 오류로 이어지지 않게 막는 현재 방침

이번 백엔드 재설계는 인프라와 문서 체계를 바꾸는 작업이지, 제품 동작을 재정의하는 작업이 아니다.

## 3. 도메인 경계

### 3.1 공통 기반

공통 기반 도메인은 다음을 담당한다.

* 인증과 인가
* 공통 응답 구조
* 오류 코드와 예외 변환
* 멱등성 저장과 재실행 제어
* 비동기 이벤트 기록과 실패 작업 추적

이 영역은 모든 도메인이 공유하는 규칙만 가진다. 예약, 대기, 현장 운영의 비즈니스 판단을 직접 소유하지 않는다.

### 3.2 매장 운영 기준 데이터

매장 운영 도메인은 예약 계산과 운영 화면의 기준 데이터를 소유한다.

* 매장
* 매장 정책
* 서비스
* 매장 멤버
* 직원 가능 서비스
* 영업시간
* 직원 스케줄
* 일정 예외

예약 가능 시간 계산은 저장된 슬롯을 조회하는 방식이 아니라 위 데이터를 조합해 계산하는 방식을 유지한다.

### 3.3 사용자와 권한

사용자 도메인은 고객 계정과 매장 멤버 권한을 분리한다.

* 한 사용자는 고객이면서 특정 매장의 직원일 수 있다.
* 운영자 권한은 매장 소속과 역할을 함께 검증한다.
* 운영자 데이터 접근은 URL의 `storeId`만으로 허용하지 않는다.

### 3.4 예약

예약 도메인은 MVP의 핵심 흐름을 소유한다.

* 예약 생성
* 내 예약 조회
* 예약 상세 조회
* 예약 취소
* 예약 상태 이력
* 운영자 체크인, 노쇼, 서비스 시작

현재 MVP 구현 기준은 다음과 같다.

* 일반 예약은 홀드 없이 즉시 `CONFIRMED`로 생성한다.
* 고객 취소는 자유 문장 `reason`만 저장한다.
* 상태 이력은 생성과 상태 변경 시 반드시 남긴다.
* 같은 고객의 겹치는 예약과 같은 자원의 충돌 예약은 허용하지 않는다.

### 3.5 예약 대기와 빈자리 제안

예약 대기 도메인은 예약 취소와 연결되는 후속 기회 제공 흐름을 소유한다.

* 예약 대기 신청
* 내 대기 목록과 상세 조회
* 대기 취소
* 빈자리 제안 생성
* 빈자리 제안 수락

핵심 규칙은 다음과 같다.

* 한 빈자리에 대해 중복 확정이 나면 안 된다.
* 제안 만료와 직접 예약은 같은 슬롯 경합으로 취급한다.
* 대기 수락 후 생성된 예약은 대기 결과로 추적 가능해야 한다.

### 3.6 현장 대기

현장 대기 도메인은 예약 외 방문 고객 흐름을 소유한다.

* 대기 가능 여부 조회
* 현장 대기 등록
* 내 현장 대기 조회
* 호출 응답
* 운영자 호출, 체크인, 취소, 복귀, 노쇼, 서비스 시작

핵심 규칙은 다음과 같다.

* 같은 고객의 중복 활성 현장 대기는 허용하지 않는다.
* 대기 번호와 앞선 대기 인원은 운영일 기준으로 일관되게 계산한다.
* 호출 만료 뒤에는 정상 응답을 받지 않는다.

### 3.7 운영자 운영 조회

운영자 조회 도메인은 고객용 도메인의 상태를 다시 가공해 매장 운영 화면에 제공한다.

* 오늘 운영 현황
* 예약 목록과 상세
* 예약 대기 목록과 상세
* 감사 로그

운영자 조회는 별도 진실의 원천이 아니다. 예약, 대기, 현장 대기 도메인이 기록한 상태를 읽기 좋은 형태로 조합하는 역할만 담당한다.

## 4. 상태 전이 원칙

상태 이름의 세부 목록은 각 상세 문서를 따른다. 다만 아래 원칙은 공통으로 유지한다.

* 상태 전이는 도메인 서비스에서만 수행한다.
* 상태 전이 성공 시 이력 저장이 빠지면 안 된다.
* 운영자 조작이 들어간 상태 전이는 감사 로그를 남긴다.
* 만료와 충돌 검증은 상태 전이 직전 최종 확인을 다시 수행한다.

## 5. 권한 경계 원칙

다음은 설계와 구현에서 항상 유지한다.

* 고객용 API는 본인 소유 데이터만 다룬다.
* 운영자용 API는 매장 멤버 자격과 역할을 함께 검증한다.
* 운영자와 고객은 같은 API 경계를 공유할 수 있지만, 같은 권한 체계를 공유하지 않는다.
* 운영자 전용 데이터는 매장 단위 멀티테넌트 검증을 통과해야 한다.

## 6. 저장 책임 원칙

각 저장 책임은 다음처럼 유지한다.

* PostgreSQL은 정합성이 중요한 기준 데이터와 상태 전이를 소유한다.
* 캐시나 임시 저장소가 도입되더라도 최종 기준 데이터는 PostgreSQL이다.
* 이벤트 재처리와 장애 분석이 필요한 비동기 기록은 추적 가능한 저장소에 남긴다.
