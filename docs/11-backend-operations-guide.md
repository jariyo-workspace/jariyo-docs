# 자리요 백엔드 운영 가이드

## 1. 문서 목적

본 문서는 자리요 백엔드를 AWS에서 운영할 때 필요한 환경 구성, 배포, 관측, 장애 대응 기준을 정리한다.

대상은 현재 MVP 기능을 그대로 유지하면서 초기 성장 구간을 안정적으로 운영하는 팀이다.

## 2. 환경 기준

권장 환경은 다음 세 가지다.

* `dev`
* `stage`
* `prod`

각 환경의 역할은 다음과 같다.

* `dev`: 개발자 기능 확인과 통합 테스트 보조
* `stage`: 운영 전 검증과 배포 리허설
* `prod`: 실제 서비스 운영

`stage`를 없애는 대신 `prod`에서 검증하지 않는다.

## 3. 설정과 시크릿 관리

원칙은 다음과 같다.

* 민감 정보는 `Secrets Manager`
* 일반 환경값은 `SSM Parameter Store`
* 이미지나 코드 저장소에 환경 비밀값 저장 금지

예:

* DB 계정 정보
* JWT private key
* 외부 연동 토큰

## 4. 배포 기준

### 4.1 기본 배포

초기 기본 배포 전략은 `Rolling Deployment`다.

이유:

* 운영 절차가 단순하다.
* ECS Fargate 기본 흐름과 잘 맞는다.
* 현재 규모에서 비용과 복잡도 증가가 적다.

### 4.2 Blue/Green 전환 조건

다음 조건이 커지면 `Blue/Green` 전환을 검토한다.

* 롤백 속도가 매우 중요해질 때
* 운영자 화면 중단 허용 폭이 줄어들 때
* 배포 실패 비용이 커질 때

## 5. 모니터링과 알람

기본 관측 수준은 다음과 같다.

* `CloudWatch Logs`
* `CloudWatch Metrics`
* 핵심 알람

핵심 알람은 최소 다음을 포함한다.

* ALB `5xx`
* ECS task 재시작 또는 비정상 종료
* RDS CPU, 연결 수, 스토리지
* Redis 메모리와 연결 이상
* 비동기 실패 작업 증가

## 6. 일상 운영 체크

운영자는 다음을 주기적으로 확인한다.

* 실패 작업 누적 여부
* RDS 성능 이상 여부
* ALB 오류 급증 여부
* 배포 후 ECS health check 통과 여부
* Redis 연결 이상 여부

## 7. 장애 대응 우선순위

장애 대응 순서는 다음과 같다.

1. 공개 API 장애 여부 확인
2. DB 연결과 쓰기 가능 여부 확인
3. ECS task 정상 수 확인
4. 비동기 작업 적체 여부 확인
5. 운영자 전용 문제인지 전체 문제인지 구분

핵심 원칙은 다음과 같다.

* 사용자 요청의 정합성을 먼저 지킨다.
* 비핵심 후처리는 지연될 수 있어도 기준 상태는 보존한다.
* 캐시나 큐 장애가 발생해도 DB 기준 흐름을 우선 살린다.

## 8. 확장 트리거

다음은 후속 아키텍처 확대 검토 신호다.

* DB가 캐시성 조회까지 과도하게 떠안을 때
* 비동기 작업량이 앱 트랜잭션 처리와 충돌할 때
* ALB 직결만으로 보안 정책 제어가 부족할 때
* 운영팀이 배포 안전성과 빠른 롤백을 더 강하게 요구할 때

이 경우 다음을 순서대로 검토한다.

* Redis 활용 범위 확대
* SQS 도입
* CloudFront와 WAF 도입
* Blue/Green 배포 도입
