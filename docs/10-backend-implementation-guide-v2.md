# 자리요 백엔드 구현 가이드 v2

## 1. 문서 목적

본 문서는 현재 MVP 동작을 유지하면서 백엔드를 계속 개발하거나 리팩터링할 때 따라야 하는 구현 기준을 정리한다.

이 문서는 다음 질문에 답한다.

* 어느 계층이 무엇을 책임지는가
* 정합성과 성능 중 무엇을 어디서 우선하는가
* Redis, Outbox, SQS 같은 보조 구성요소를 어떤 원칙으로 붙이는가
* 새 기능이 들어와도 무엇은 절대 바꾸지 말아야 하는가

## 2. 구현 원칙

### 2.1 도메인 우선

구현 판단의 시작점은 엔티티보다 도메인 규칙이다.

다음은 항상 먼저 확인한다.

* 상태 전이 규칙
* 소유권 규칙
* 멱등성 요구 여부
* 최종 정합성 검증 지점

### 2.2 무상태 애플리케이션

Fargate 환경을 전제로 애플리케이션 인스턴스는 무상태를 유지한다.

따라서 다음을 금지한다.

* 인메모리 세션을 기준 데이터처럼 사용하는 방식
* 단일 인스턴스 로컬 캐시에만 의존하는 흐름
* 배포나 재시작 시 유실되면 안 되는 상태를 로컬 메모리에 두는 방식

### 2.3 PostgreSQL 우선 정합성

정합성이 중요한 데이터는 PostgreSQL을 기준 저장소로 유지한다.

예:

* 예약 충돌 방지
* 상태 전이
* 상태 이력
* 감사 로그
* 멱등성 기록

Redis나 메시지 큐가 들어오더라도 최종 승인과 상태 전이는 DB 트랜잭션 기준으로 판단한다.

## 3. 계층 책임

### 3.1 Controller

Controller는 다음만 담당한다.

* 인증 주체 전달
* 요청 파라미터 파싱과 유효성 검증
* 응답 포맷 변환

상태 전이, 권한 판단, 충돌 해결은 Controller에 두지 않는다.

### 3.2 Service

Service는 도메인 유스케이스의 진입점이다.

Service는 다음을 담당한다.

* 도메인 규칙 적용
* 권한과 소유권 검증 호출
* 락과 멱등성 적용 지점 결정
* 트랜잭션 단위 조정
* 상태 이력과 감사 로그 기록

### 3.3 Repository

Repository는 저장과 조회 전략을 숨긴다.

Repository는 다음 역할에 집중한다.

* 필요한 락 쿼리 제공
* 도메인 판단에 필요한 최소 조회 제공
* 정렬과 커서 페이지네이션 제공

도메인 규칙 자체를 Repository 안으로 밀어 넣지 않는다.

## 4. 저장 위치 원칙

### 4.1 PostgreSQL에 둘 것

* 기준 데이터
* 상태 전이 결과
* 재현 가능한 이력
* 멱등성 결과
* 아웃박스

### 4.2 Redis에 둘 것

도입 시 다음만 우선 검토한다.

* 짧은 TTL 캐시
* 반복 계산 결과
* DB 보호를 위한 임시성 조회 최적화

다음은 Redis 단독 기준으로 두지 않는다.

* 예약 확정 여부
* 권한의 최종 진실
* 상태 전이의 최종 기록

### 4.3 SQS에 둘 것

도입 시 다음에 사용한다.

* 비동기 후처리 격리
* 재시도와 DLQ가 필요한 작업
* 소비자 수평 확장이 필요한 작업

단, 현재 기본값은 `DB Outbox`이며 SQS는 성장 트리거가 확인된 뒤 도입한다.

## 5. 트랜잭션과 동시성

### 5.1 예약과 대기

예약, 대기, 빈자리 제안은 경합 가능성이 높으므로 다음을 유지한다.

* 최종 상태 변경 직전 재검증
* 필요한 경우 행 잠금 사용
* 멱등성으로 중복 실행 차단

### 5.2 현장 대기

현장 대기는 운영일과 대기 순서 계산이 중요하므로 다음을 유지한다.

* 활성 대기 중복 금지
* 호출 만료 시각 검증
* 대기 앞 인원 재계산 일관성 유지

### 5.3 운영자 처리

운영자 체크인, 노쇼, 서비스 시작과 완료는 다음을 유지한다.

* 상태 전이 전 현재 상태 재확인
* 매장 소속과 역할 재검증
* 이력과 감사 로그 동시 기록

## 6. 권한과 API 경계

고객과 운영자는 같은 API 서비스에 들어오더라도 다음을 구분한다.

* 고객 API는 본인 데이터만 허용
* 운영자 API는 매장 멤버 역할 검증 필수
* `storeId`는 힌트일 뿐이며 접근 허용의 근거가 아니다

운영자 전용 도메인을 별도 애플리케이션으로 분리하지 않는다. 현재 단계에서는 같은 API 경계 안에서 권한으로만 분리한다.

## 7. 테스트 전략

### 7.1 단위 테스트

다음을 우선 검증한다.

* 상태 전이
* 권한 규칙
* 서비스별 예외 처리

### 7.2 통합 테스트

다음을 우선 검증한다.

* 예약 경합
* 대기 수락과 직접 예약 충돌
* 현장 대기 전체 흐름
* 운영자 체크인과 서비스 완료 흐름

### 7.3 문서 변경 시 확인

문서가 바뀌더라도 다음 테스트 기준은 유지한다.

* `test`
* `integrationTest`

문서가 구현을 잘못 설명하면 문서를 수정한다. 구현을 바꾸지 않는 리디자인에서는 테스트를 문서에 맞추지 않는다.

## 8. 변경 체크리스트

새 기능이나 리팩터링 전에는 다음을 확인한다.

* 현재 MVP API 계약을 깨지 않는가
* 상태 전이와 이력이 유지되는가
* 운영자 권한 검증이 빠지지 않았는가
* 정합성 판단이 캐시나 비동기 계층으로 밀리지 않았는가
* 테스트로 기존 핵심 시나리오를 다시 확인했는가
