# 자리요 백엔드 시스템 아키텍처 가이드

## 1. 문서 목적

본 문서는 자리요 백엔드를 AWS 위에서 어떻게 운영할지 정리한 시스템 아키텍처 기준 문서다.

대상은 현재 구현된 MVP를 그대로 서비스하면서 초기 성장 구간을 안정적으로 버티는 구조다.

고정 전제는 다음과 같다.

* 컴퓨트는 `ECS Fargate`를 사용한다.
* 가용성 기준은 단일 리전 멀티 AZ다.
* ALB는 public subnet에 둔다.
* 애플리케이션, DB, Redis는 private subnet에 둔다.
* 운영자와 고객은 같은 API 경계를 사용하고 권한으로만 분리한다.
* 가장 중요한 의사결정 기준은 운영 단순성이다.

## 2. 비교할 세 가지 안

### 2.1 단순안

구성:

* `Route 53`
* `ALB`
* `ECS Fargate`
* `RDS PostgreSQL Multi-AZ`
* `CloudWatch`
* `Secrets Manager + SSM`

비동기:

* PostgreSQL 기반 `DB Outbox`

장점:

* 구성 요소 수가 가장 적다.
* 운영과 장애 파악이 단순하다.
* 현재 MVP와 가장 자연스럽게 연결된다.

단점:

* 캐시, 임시 상태, 토큰성 부하가 DB로 더 몰린다.
* 성장 구간에서 DB 집중이 빨리 나타날 수 있다.

적합한 경우:

* 트래픽이 아직 낮고 운영 인력이 매우 적을 때
* Redis와 큐 운영 부담을 당장 피해야 할 때

### 2.2 균형안

구성:

* `Route 53`
* `ALB`
* `ECS Fargate`
* `RDS PostgreSQL Multi-AZ`
* `ElastiCache Redis`
* `CloudWatch`
* `Secrets Manager + SSM`

비동기:

* PostgreSQL 기반 `DB Outbox`

장점:

* 정합성은 DB가 유지하고, 임시성 또는 캐시성 부하는 Redis로 분리할 수 있다.
* 현재 MVP 구현과의 간극이 작다.
* 초기 성장 구간에서 가장 무난한 확장 여지를 가진다.

단점:

* 단순안보다 운영 대상이 하나 늘어난다.
* Redis 장애 시 우회 전략이 필요하다.

적합한 경우:

* MVP를 빠르게 운영하되 성능 병목을 미리 완화하고 싶을 때
* 운영 복잡도와 성장 대응을 균형 있게 가져가야 할 때

### 2.3 확장안

구성:

* `Route 53`
* `CloudFront`
* `AWS WAF`
* `ALB`
* `ECS Fargate`
* `RDS PostgreSQL Multi-AZ`
* `ElastiCache Redis`
* `SQS`
* `CloudWatch`
* `Secrets Manager + SSM`

비동기:

* `SQS` 중심 비동기 처리

장점:

* 엣지 보안과 요청 제어가 강화된다.
* 비동기 작업의 격리와 재시도 운영성이 좋아진다.
* 트래픽 증가와 비동기 폭증 상황에 더 유리하다.

단점:

* 구성 요소가 많아진다.
* 운영 난이도와 비용이 증가한다.
* 현재 MVP 기준에서는 일부 구성요소가 과할 수 있다.

적합한 경우:

* 봇 차단, 규칙 기반 필터링, 큐 기반 격리가 필요해질 때
* 팀이 운영 복잡도를 감당할 준비가 되었을 때

## 3. 권장안

현재 자리요 백엔드의 권장안은 `균형안`이다.

권장 구성은 다음과 같다.

* `Route 53 -> ALB -> ECS Fargate`
* `ECS Fargate -> RDS PostgreSQL Multi-AZ`
* `ECS Fargate -> ElastiCache Redis`
* 비동기는 당분간 `DB Outbox`
* 운영 가시성은 `CloudWatch Logs`, `CloudWatch Metrics`, 핵심 알람

권장 이유는 다음과 같다.

* 현재 MVP 동작을 바꾸지 않고 도입 가능하다.
* DB가 모든 임시 상태를 함께 떠안는 구조를 피할 수 있다.
* 큐와 엣지 계층을 한 번에 늘리지 않아도 된다.
* 운영 단순성을 해치지 않으면서 초기 성장 구간의 여유를 확보할 수 있다.

## 4. 네트워크와 보안 기준

### 4.1 네트워크

기본 네트워크 구조는 다음과 같다.

* VPC는 단일 리전에 멀티 AZ로 구성한다.
* ALB만 public subnet에 둔다.
* ECS Fargate task는 private subnet에 둔다.
* RDS와 Redis는 외부에서 직접 접근되지 않는 private subnet에 둔다.

### 4.2 보안

기본 보안 원칙은 다음과 같다.

* ECS task에만 DB 접근 보안 그룹을 연다.
* Redis도 ECS task에서만 접근 가능하게 둔다.
* 애플리케이션 비밀값은 코드와 이미지에 포함하지 않는다.
* 민감 정보는 `Secrets Manager`, 일반 설정은 `SSM Parameter Store`를 사용한다.

## 5. 데이터 계층 기준

### 5.1 PostgreSQL

PostgreSQL은 다음의 최종 기준 저장소다.

* 예약, 대기, 현장 대기, 서비스 세션 상태
* 상태 이력
* 멱등성 기록
* 비동기 아웃박스
* 감사 로그

### 5.2 Redis

Redis를 도입하면 아래 용도를 우선 검토한다.

* 캐시성 조회 데이터
* 토큰 또는 임시 인증 보조 정보
* 반복 계산 결과의 짧은 TTL 저장
* 트래픽 급증 시 DB 보호용 읽기 우회

Redis가 도입되더라도 정합성의 최종 기준은 PostgreSQL이다.

## 6. 비동기 처리 기준

현재 권장 기본값은 `DB Outbox`다.

이유는 다음과 같다.

* 현재 구현과 자연스럽게 이어진다.
* 별도 메시지 인프라 없이 추적 가능성이 높다.
* 운영 단순성 기준에 맞다.

`SQS`는 아래 조건이 나타나면 후속 권장안으로 승격한다.

* 작업량 급증으로 앱 트랜잭션과 비동기 작업 격리가 필요할 때
* 소비자 수평 확장이 필요할 때
* 재시도 전략과 dead-letter queue 운영이 필요할 때

## 7. 배포와 환경

### 7.1 환경

권장 환경 구성은 다음과 같다.

* `dev`
* `stage`
* `prod`

`stage`는 운영 전 검증과 배포 리허설을 위한 환경으로 유지한다.

### 7.2 배포 전략

초기 기본값은 `Rolling Deployment`다.

다음 조건이 커지면 `Blue/Green`을 검토한다.

* 트래픽 손실 비용이 커질 때
* 롤백 시간 단축이 중요해질 때
* 운영자 화면 중단 허용 폭이 줄어들 때

## 8. 관측과 알람

기본 운영 가시성은 다음 수준으로 둔다.

* `CloudWatch Logs`
* `CloudWatch Metrics`
* 핵심 알람

핵심 알람 대상:

* ALB 5xx 증가
* ECS task 비정상 재시작
* RDS CPU와 연결 수 급증
* Redis 메모리와 연결 상태
* 비동기 실패 작업 증가

## 9. 요청과 데이터 흐름

### 9.1 고객과 운영자 요청

고객과 운영자 요청은 같은 API 서비스로 들어온다.

분리 방식은 다음과 같다.

* 경계는 동일하게 유지한다.
* 인증 주체와 매장 권한을 통해 접근을 구분한다.
* 운영자 데이터는 매장 소속 검증을 통과해야만 처리한다.

### 9.2 비동기 후처리

예약 취소, 빈자리 제안, 알림 기록 같은 후처리는 다음 원칙을 따른다.

* 기준 상태 변경은 먼저 DB 트랜잭션에서 끝낸다.
* 후처리는 아웃박스 또는 큐를 통해 재시도 가능하게 처리한다.
* 장애가 발생해도 사용자 요청의 핵심 정합성은 우선 보존한다.

## 10. 채택하지 않은 안의 이유

단순안을 현재 권장안으로 채택하지 않은 이유:

* 운영은 쉽지만 성장 구간에서 DB 집중이 빠르게 올 수 있다.

확장안을 현재 권장안으로 채택하지 않은 이유:

* WAF, CloudFront, SQS를 한 번에 도입하면 운영 대상이 과하게 늘어난다.
* 현재 MVP 규모와 운영 단순성 우선 기준에 비해 무겁다.
