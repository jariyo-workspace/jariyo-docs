# 자리요 백엔드 시스템 아키텍처 가이드

## 1. 문서 목적

본 문서는 자리요 백엔드를 AWS 위에서 어떻게 운영하고 배포할지 정리한 시스템 아키텍처 기준 문서다.

대상은 현재 구현된 MVP를 그대로 서비스하면서 초기 성장 구간을 안정적으로 버티는 구조다.

고정 전제는 다음과 같다.

* 컴퓨트는 `ECS Fargate`를 사용한다.
* 가용성 기준은 단일 리전 멀티 AZ다.
* ALB는 public subnet에 둔다.
* 애플리케이션, DB, Redis는 private subnet에 둔다.
* 운영자와 고객은 같은 API 경계를 사용하고 권한으로만 분리한다.
* 가장 중요한 의사결정 기준은 운영 단순성이다.

## 2. 최종 권장 아키텍처

현재 자리요 백엔드의 최종 권장 아키텍처는 아래와 같다.

* `Route 53 -> ALB -> ECS Fargate(API)`
* `ECS Fargate(Worker)`는 외부 트래픽을 받지 않는다.
* `API`와 `Worker`는 모두 private subnet에 둔다.
* `RDS PostgreSQL Multi-AZ`를 기준 저장소로 사용한다.
* `ElastiCache Redis`는 캐시와 임시 상태 보조 용도로만 사용한다.
* 비동기 후처리는 `DB Outbox`를 `Worker`가 소비하는 구조로 운영한다.
* `Secrets Manager + SSM Parameter Store`로 시크릿과 일반 환경값을 분리한다.
* 공개 경계는 현재 `ALB 직결`이며, `WAF`는 확장 옵션으로 둔다.

### 2.1 권장 구성 요소

필수 구성 요소:

* `Route 53`
* `ALB`
* `ECS Cluster`
* `ECS Service: API`
* `ECS Service: Worker`
* `RDS PostgreSQL Multi-AZ`
* `ElastiCache Redis`
* `CloudWatch Logs`
* `CloudWatch Metrics`
* `Secrets Manager`
* `SSM Parameter Store`

선택 구성 요소:

* `AWS WAF`
* `Blue/Green Deployment`
* `SQS`

### 2.2 API와 Worker를 나누는 이유

현재 권장안은 `API 1개 + Worker 1개` 구조다.

`API`는 다음을 담당한다.

* 고객과 운영자 요청 처리
* 동기 상태 변경
* DB 트랜잭션 종료

`Worker`는 다음을 담당한다.

* Outbox 소비
* 후처리 재시도
* 비동기 실패 작업 복구
* 스케줄성 후처리 작업

이 구조를 채택하는 이유는 다음과 같다.

* 비동기 후처리 부하가 API 지연으로 번지지 않는다.
* 장애 위치를 API와 Worker로 나눠 파악하기 쉽다.
* 추후 메시지 큐나 별도 소비자로 확장하기 쉽다.

### 2.3 단일 이미지 원칙

초기 운영 단순성을 위해 `API`와 `Worker`는 가능하면 같은 컨테이너 이미지를 사용한다.

차이는 다음으로만 둔다.

* 실행 명령
* 환경 변수
* health check
* autoscaling 정책

이미지를 분리하는 시점은 다음 조건이 생긴 뒤로 미룬다.

* 릴리즈 주기가 크게 달라질 때
* 종속성이 분명히 갈릴 때
* 이미지 크기와 빌드 시간이 운영 부담이 될 때

## 3. 비교안 요약

### 3.1 단순안

* `Route 53`
* `ALB`
* `ECS Fargate(API 단일 서비스)`
* `RDS PostgreSQL Multi-AZ`
* `CloudWatch`
* `Secrets Manager + SSM`

비동기:

* PostgreSQL 기반 `DB Outbox`

장점:

* 구성 요소 수가 가장 적다.
* 운영과 장애 파악이 단순하다.
* 현재 MVP와 가장 자연스럽게 연결된다.

단점:

* 캐시, 임시 상태, 토큰성 부하가 DB로 더 몰린다.
* 성장 구간에서 DB 집중이 빨리 나타날 수 있다.

적합한 경우:

* 트래픽이 아직 낮고 운영 인력이 매우 적을 때
* Redis와 큐 운영 부담을 당장 피해야 할 때

### 3.2 균형안

구성:

* `Route 53`
* `ALB`
* `ECS Fargate(API + Worker)`
* `RDS PostgreSQL Multi-AZ`
* `ElastiCache Redis`
* `CloudWatch`
* `Secrets Manager + SSM`

비동기:

* PostgreSQL 기반 `DB Outbox`

장점:

* 정합성은 DB가 유지하고, 임시성 또는 캐시성 부하는 Redis로 분리할 수 있다.
* 현재 MVP 구현과의 간극이 작다.
* 초기 성장 구간에서 가장 무난한 확장 여지를 가진다.

단점:

* 단순안보다 운영 대상이 하나 늘어난다.
* Redis 장애 시 우회 전략이 필요하다.

적합한 경우:

* MVP를 빠르게 운영하되 성능 병목을 미리 완화하고 싶을 때
* 운영 복잡도와 성장 대응을 균형 있게 가져가야 할 때

### 3.3 확장안

구성:

* `Route 53`
* `AWS WAF`
* `ALB`
* `ECS Fargate(API + Worker)`
* `RDS PostgreSQL Multi-AZ`
* `ElastiCache Redis`
* `SQS`
* `CloudWatch`
* `Secrets Manager + SSM`

비동기:

* `SQS` 중심 비동기 처리

장점:

* 엣지 보안과 요청 제어가 강화된다.
* 비동기 작업의 격리와 재시도 운영성이 좋아진다.
* 트래픽 증가와 비동기 폭증 상황에 더 유리하다.

단점:

* 구성 요소가 많아진다.
* 운영 난이도와 비용이 증가한다.
* 현재 MVP 기준에서는 일부 구성요소가 과할 수 있다.

적합한 경우:

* 봇 차단, 규칙 기반 필터링, 큐 기반 격리가 필요해질 때
* 팀이 운영 복잡도를 감당할 준비가 되었을 때

## 4. 권장안 선정 이유

현재 단계에서 `균형안`을 권장안으로 유지하는 이유는 다음과 같다.

* 현재 MVP 동작을 바꾸지 않고 배포 구조만 현실적으로 강화할 수 있다.
* `API + Worker` 분리로 운영 단순성과 장애 격리를 같이 확보할 수 있다.
* Redis를 넣되 기준 저장소는 DB로 유지해 복잡도를 통제할 수 있다.
* 모바일 앱 백엔드이므로 `CloudFront` 없이도 충분하고, `WAF`는 필요 시 점진적으로 붙일 수 있다.
* `SQS` 없이도 Outbox 구조로 후처리 유실 방지 요구를 충족할 수 있다.

## 5. 네트워크와 보안 기준

### 5.1 네트워크

기본 네트워크 구조는 다음과 같다.

* VPC는 단일 리전에 멀티 AZ로 구성한다.
* ALB만 public subnet에 둔다.
* `API`, `Worker` task는 모두 private subnet에 둔다.
* RDS와 Redis는 외부에서 직접 접근되지 않는 private subnet에 둔다.
* DB와 Redis는 서로 다른 보안 그룹으로 관리한다.

### 5.2 보안

기본 보안 원칙은 다음과 같다.

* `API`와 `Worker` task에만 DB 접근 보안 그룹을 연다.
* Redis도 `API`, `Worker`에서만 접근 가능하게 둔다.
* 애플리케이션 비밀값은 코드와 이미지에 포함하지 않는다.
* 민감 정보는 `Secrets Manager`, 일반 설정은 `SSM Parameter Store`를 사용한다.
* 운영자와 고객은 같은 API 경계를 공유하지만, 권한 검증은 애플리케이션 계층에서 분리한다.
* `WAF`는 현재 필수 구성요소가 아니며, 비정상 호출 증가 시 ALB 앞에 추가한다.

## 6. 데이터 계층 기준

### 6.1 PostgreSQL

PostgreSQL은 다음의 최종 기준 저장소다.

* 예약, 대기, 현장 대기, 서비스 세션 상태
* 상태 이력
* 멱등성 기록
* 비동기 아웃박스
* 감사 로그
* 실패 후처리 추적 정보

### 6.2 Redis

Redis를 도입하면 아래 용도를 우선 검토한다.

* 캐시성 조회 데이터
* 토큰 또는 임시 인증 보조 정보
* 반복 계산 결과의 짧은 TTL 저장
* 트래픽 급증 시 DB 보호용 읽기 우회

Redis가 도입되더라도 정합성의 최종 기준은 PostgreSQL이다.

Redis 장애 시에는 캐시 기능을 축소하고 DB 기준으로 계속 운영 가능한 구조를 유지한다.

## 7. 비동기 처리 기준

현재 권장 기본값은 `DB Outbox`다.

이유는 다음과 같다.

* 현재 구현과 자연스럽게 이어진다.
* 별도 메시지 인프라 없이 추적 가능성이 높다.
* 운영 단순성 기준에 맞다.
* 예약 취소, 빈자리 제안, 실패 작업 재처리의 유실 방지를 설계에 포함할 수 있다.

권장 흐름은 다음과 같다.

1. API가 DB 트랜잭션에서 기준 상태를 먼저 변경한다.
2. 같은 트랜잭션에서 Outbox 레코드를 저장한다.
3. Worker가 Outbox를 읽어 후처리를 수행한다.
4. 실패 시 재시도와 실패 작업 추적을 남긴다.

`SQS`는 아래 조건이 나타나면 후속 권장안으로 승격한다.

* 작업량 급증으로 앱 트랜잭션과 비동기 작업 격리가 필요할 때
* 소비자 수평 확장이 필요할 때
* 재시도 전략과 dead-letter queue 운영이 필요할 때

## 8. 배포와 환경

### 8.1 환경

권장 환경 구성은 다음과 같다.

* `dev`
* `stage`
* `prod`

환경별 역할은 다음과 같다.

* `prod`: 실제 운영 환경, Multi-AZ와 모든 핵심 알람 적용
* `stage`: prod 사전 검증 환경, 구조는 같고 규모는 축소 가능
* `dev`: 로컬 중심, 필요 시 최소 원격 환경만 유지

`stage`는 운영 전 검증과 배포 리허설을 위한 환경으로 반드시 유지한다.

### 8.2 배포 전략

초기 기본값은 `Rolling Deployment`다.

다음 조건이 커지면 `Blue/Green`을 검토한다.

* 트래픽 손실 비용이 커질 때
* 롤백 시간 단축이 중요해질 때
* 운영자 화면 중단 허용 폭이 줄어들 때

## 9. 서비스별 운영 기준

### 9.1 API 서비스

기본 운영 기준:

* ALB target group 연결
* health check 필수
* autoscaling 대상
* 고객과 운영자 요청 공통 처리

### 9.2 Worker 서비스

기본 운영 기준:

* 외부 target group 없음
* Outbox 소비와 재처리 전담
* 배포 후 API보다 늦게 올라와도 된다.
* API와 별도로 스케일링 가능해야 한다.

## 10. 관측과 알람

기본 운영 가시성은 다음 수준으로 둔다.

* `CloudWatch Logs`
* `CloudWatch Metrics`
* 핵심 알람

핵심 알람 대상:

* ALB 5xx 증가
* ECS task 비정상 재시작
* RDS CPU와 연결 수 급증
* Redis 메모리와 연결 상태
* 비동기 실패 작업 증가

## 11. 요청과 데이터 흐름

### 11.1 고객과 운영자 요청

고객과 운영자 요청은 같은 API 서비스로 들어온다.

분리 방식은 다음과 같다.

* 경계는 동일하게 유지한다.
* 인증 주체와 매장 권한을 통해 접근을 구분한다.
* 운영자 데이터는 매장 소속 검증을 통과해야만 처리한다.

### 11.2 비동기 후처리

예약 취소, 빈자리 제안, 알림 기록 같은 후처리는 다음 원칙을 따른다.

* 기준 상태 변경은 먼저 DB 트랜잭션에서 끝낸다.
* 후처리는 아웃박스 또는 큐를 통해 재시도 가능하게 처리한다.
* 장애가 발생해도 사용자 요청의 핵심 정합성은 우선 보존한다.

## 12. 채택하지 않은 안의 이유

단순안을 현재 권장안으로 채택하지 않은 이유:

* 운영은 쉽지만 성장 구간에서 DB 집중이 빠르게 올 수 있다.

확장안을 현재 권장안으로 채택하지 않은 이유:

* WAF와 SQS를 한 번에 도입하면 운영 대상이 과하게 늘어난다.
* 현재 MVP 규모와 운영 단순성 우선 기준에 비해 무겁다.
